Method

A workflow you can audit at every step.

No mystery, no remote access you cannot see, no promises that depend on luck. This is the exact sequence behind a MZAZI TECH demonstration.

01 — Intake

You submit a demo request with the device model, Android version where known, and the module you want to see. We reply within one business day.

Form → reference ID

02 — Verification

Before any session we confirm who you are, that the device is yours (or that you administer it), and what the demonstration may cover.

Ownership & authority

03 — Scoping

We write down the scope: modules, expected outputs, duration and the list of actions that will not be taken. You approve it before we begin.

Written scope, no surprises

04 — Demonstration session

A 20–30 minute screen-shared walkthrough using reference profiles and simulated data. You can ask questions at any point.

20–30 minutes

05 — Report handover

You receive the sample report pack: diagnostic sheet, lock-state summary, IMEI structure notes and a boundary checklist. Every page is watermarked DEMO.

PDF-ready pack

06 — Follow-up

One clarification round is included. If your case needs a real service, we tell you which authorised provider to approach — and what to ask them.

Referral, not a sales pitch

Operating principles

Three rules that shape every session.

Consent before capability

If authority is unclear, we stop. A demonstration is never a reason to skip verification, and a deadline never overrides it.

Everything is observable

You see each step on screen. There is no background process, no hidden command and no unexplained delay.

Claims match evidence

We report only what the demonstration produced. No device is described as unlocked, repaired or verified when it was not.

Inside the report

What you actually receive.

The demonstration pack mirrors a professional service record — minus any real device data. Each section is designed to be readable by a non-technical client.

  • Cover sheet — reference ID, date, scope, and a visible DEMO classification.
  • Diagnostic sheet — battery, storage, thermal and patch-level fields with interpretation notes.
  • Lock-state summary — field-by-field explanation of what each indicator means.
  • IMEI structure page — TAC, serial segment, checksum result and its limitations.
  • Boundary checklist — what was not done, and why, signed off by the operator.
